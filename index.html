Field guide / 2026

AI駆動開発の要諦

人が決める。AIが繰り返す。
実装の速さを、検証で仕事の成果に変える。

AI駆動開発の要諦は、人が目的・制約・完了条件を決め、AIが実装と検証を繰り返せる環境をつくることです。コード生成にとどまらず、要件整理から調査、実装、テスト、レビューまでをつなげます。業務判断と変更受入の責任は、人が持ちます。

Five principles

検証できる仕事に変える5原則

  1. 01

    完了条件

    入力・出力・例外時の動作を明文化する。

  2. 02

    必要な文脈

    関連コード、仕様、実行コマンド、失敗ログを渡す。

  3. 03

    小さな変更

    1機能または1不具合ごとに、差分と動作を確かめる。

  4. 04

    結果確認

    テスト、実画面、実ファイル、保存先の状態で確かめる。

  5. 05

    権限管理

    ローカル修正、本番変更、外部送信、削除それぞれの許可範囲を決める。

Three settings

指示・権限・検証を整える3設定

SETTING 01

AGENTS.md — 行動のルール

グローバル側と案件側の指示を読ませ、繰り返す案件ルールと、実際に動く検証コマンドを置きます。長い背景や一度限りの手順は別資料へ分けます。

以下はJavaScript / TypeScript案件の例です。コマンドは案件に合わせて変えてください。

公式ドキュメント ↗
# 作業ルール
- 変更前に関連コードと既存テストを確認する。
- 既存の設計とユーザーの変更を保持する。
- 依頼に関係する範囲だけ変更する。

# 検証
- 型検査: npm run typecheck
- 静的検査: npm run lint
- テスト: npm test
- ビルド: npm run build
- UI変更では実画面を確認する。
- 不具合修正では、修正前の再現と修正後の解消を確認する。

# 境界と報告
- 秘密情報をコードやログへ出さない。
- 本番反映・外部送信・削除は、許可された範囲に従う。
- 完了時に変更内容、検証結果、未確認事項を報告する。
SETTING 02

config.toml — 技術的な制限

ユーザー側の $env:USERPROFILE\.codex\config.toml に共通設定を置き、信頼した案件では .codex/config.toml で上書きできます。編集前に既存キーとテーブルの重複を確認します。

CLI / IDE向けの例です。コマンドの書き込みはワークスペース中心、コマンドのネットワーク接続は既定で無効。権限拡張は承認対象です。環境や組織ポリシーによって適用範囲は変わります。

区別: AGENTS.mdは行動指示、技術的制限はsandboxやサービス権限で行います。このネットワーク設定だけでWeb検索や接続アプリの全経路が止まるわけではありません。

基本設定 ↗Sandboxと承認 ↗
approval_policy = "on-request"
sandbox_mode = "workspace-write"
model_reasoning_effort = "medium"

[sandbox_workspace_write]
network_access = false
SETTING 03

CI — 継続的な検証

GitHub Actionsなどで型検査、静的検査、テスト、ビルドを実行し、必要な検査の成功をマージ条件にします。UIは実画面、外部連携は応答と保存結果を確認します。認証、課金、削除、権限変更は、人も差分と動作を確認します。

Request template

依頼文に「正解の物差し」を入れる

目的: 顧客一覧から会社名で検索できるようにする。

対象: 顧客一覧画面と検索API。

受入条件:
- 会社名の部分一致で検索できる。
- 空欄なら全件を表示する。
- 0件なら「該当する顧客がありません」と表示する。
- 権限のない顧客データを取得・表示できない。

進め方: 関連実装を調べ、影響範囲を示してから実装する。必要なテストと画面確認を行い、不具合があれば修正する。最後に変更内容、検証結果、未確認事項を報告する。

制約: 既存の認証方式を保持する。本番デプロイは今回の対象外。

POINT

AI自身が正誤を確かめられるか

受入条件には、正常系だけでなく、空欄、0件、権限違反まで含めます。

Six cautions

自動化しても、手放しにしない

  1. 1

    一度に大きく作らせない。1機能ずつ実装し、差分と結果を確かめる。

  2. 2

    業務ルールと照合する。実装とテストが同じ誤解に基づけば、テストは通ってしまう。既知の正解と比べる。

  3. 3

    差分で逃げ道を確かめる。テストの削除、エラーの握りつぶし、型チェックの回避を確認する。

  4. 4

    .gitignore を読取り禁止と考えない。これはGitへの登録を防ぐ設定であり、AIやツールからの読取りを禁止する仕組みではない。

  5. 5

    並列作業は所有範囲を分ける。担当ファイルや作業用のチェックアウトを分け、競合を防ぐ。

  6. 6

    生成速度だけで測らない。要件整理、レビュー、修正を含む時間と、リリース後の不具合も測定する。

First step

入出力を照合できる、小さな案件から

実施済みの事例ではなく、業務導入の候補です。まずは正解を照合しやすい機能を選びます。

  • 議事録から宿題候補を抽出する
  • 提案トラッキングの重複登録を防ぐ
  • 企業調査の結果を指定JSONへ変換する

1各案件で実際に動く検証コマンドを整える

2代表的な入力と期待結果を用意する

3小案件で着手し、受入時間・手戻り・レビュー時間・利用料を記録する
